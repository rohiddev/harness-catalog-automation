⏺ Here's the honest picture:

  Native IDP constraint: type: array renders all items fully inline — no modal, no collapse. There is no native way to replicate Jarvis's summary table + edit modal pattern.

  With 25 items × ~20 fields each = ~500 visible fields — the form works, it's just long.

  ---
  Practical mitigations:

  1. Split webs and apps onto separate pages

  Put Section B fields on page 2, webs on page 3, apps on page 4. Users deal with one array at a time instead of both on one endless page.

  2. Good defaults reduce real scroll time

  Most fields already have defaults (isBifrost: true, instanceSize: Medium, volumeSize: 40, loadbalancer: None, all booleans false). In practice a user adds a row and only types repositoryName
  and picks os — the rest is pre-filled. 2-3 rows is fast even if they're fully expanded.

  3. For 25-row testing — pipeline side has no issue

  The pipeline receives webs and apps as JSON arrays regardless of size and passes them straight into the Jarvis POST body. No limit, no extra handling needed. The 25-row concern is purely a form
   scroll UX issue.

  4. ui:options: collapsible: true — worth a quick test

  RJSF-material-ui supports collapsible array items, but it's not confirmed working in Harness IDP. If it works, each added item would collapse to a title row by default and expand on click —
  solves the 25-row UX completely.

  ---
  Recommended build approach:

  - Page 2: Section B top-level fields (applicationName, environment, multiRegionDeployment, etc.)
  - Page 3: webs array only
  - Page 4: apps array + isDbTier + submit

  This way 25 web tier rows are on their own page and 25 app tier rows are on their own page — manageable even without collapse.


  ====
   Honest options if collapsible doesn't work:

    Option 1 — Accept it (recommended for now)

    In production, users add 2-3 tiers with mostly default values. They type repositoryName, pick os, done. The long page is a test-only problem — real usage is fast. Ship it, document the known UX
     gap, revisit if users complain.

    Option 2 — Strip the array down to core fields only

    Move lambda_config and lb_config out of the tier array entirely. Make them a separate page 5 ("Advanced Config") with a text field asking which tier the config applies to. This cuts each inline
     item from ~20 fields to ~12, halving the scroll length. Trade-off: two-step UX for lambda/LB users.

    Option 3 — Pre-populate tiers from the lookup API response

    If the lookup POST (Call 1) returns existing tier data for the SYSID, use setContextData to store it and try to inject it as array defaults. This means users review/edit pre-filled rows instead
     of building from scratch. Unconfirmed whether getContextData works as an array default in Harness IDP — would need a test.

    Option 4 — Raise with Harness support

    Log a support ticket requesting collapsible array items. This is a known gap vs Backstage community templates which have had accordion arrays in some plugin implementations. Worth raising — if
    it ships in a future release it's a zero-cost fix.

    Option 5 — Custom plugin

    Table + modal is achievable as a plugin. Stakeholder said hard no on custom plugins — off the table unless that decision changes.

    Recommendation: Ship with Option 1 now. File the Harness support ticket (Option 4) in parallel. If the lookup API returns tier data, prototype Option 3 — it solves the problem cleanly if it
    works.
